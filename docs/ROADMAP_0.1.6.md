# Magic Video v0.1.6 需求规划

> 状态：**规划中，未开发**（当前版本 v0.1.5，已发版）。本文件是下一版本的需求清单与实施方案，不是已实现功能。
> 需求基线见 `AGENTS.md` 第 1 节；调研依据见 `docs/OPTIMIZATION.md`；已实现能力见 `docs/FEATURES.md`；实现细节见 `docs/IMPLEMENTATION_NOTES.md`。
> 重要等级按「纯本地个人工具」定位排定（无账号 / 无云 / 无定时任务），与 OPTIMIZATION 原始 P0–P3 略有差异。
> 复杂度：小 <0.5 人日 / 中 1–3 人日 / 大 >1 人周。

---

## 1. 本版目标

一句话：**补数据地基，去掉续播最常见的两类投诉，让历史数据可备份、可迁移、不丢。**

v0.1.5 功能已相当完整（导入/媒体库/追剧/播控/搜索/封面/历史/黑名单/Obsidian 全部可用），本版不铺新功能面，集中处理三类已识别的薄弱处：

| 补强方向 | 当前问题 | 本版对应需求 |
|---|---|---|
| A. 数据地基薄弱 | 进度以文件路径为主键，移动/换盘即丢；数据只在单个 SQLite 库，误删全损；并发写无写队列 | P0-2、P0-4、P1-6、P1-3 |
| B. 边界不完整 | 完成阈值硬编码 90%；批量纠错缺失；倍速 0.1 步进到不了 1.25×；全盘快搜本机需手开 HTTP | P0-1、P0-3、P2-5 |
| C. 外部依赖脆弱 | 封面/网页搜索依赖站点 HTML 结构；缓存键口径易回退；WiX 安装器未真机验证；Obsidian 路线图解析耦合 | 见第 4 节「三项补强方案」 |

### 2.1 P0 · 最高优先（建议本版全做）

| 编号 | 需求 | 价值 | 复杂度 | 验收要点 |
|---|---|---|---|---|
| P0-1 | **完成判定三阈值可配置** | 消除「点开 3 秒生成续播」「剩 5 分钟判没看」两类投诉 | 小 | 设置页可配 `min_resume_percent=5` / `ignore_seconds_at_start=180` / `ignore_percent_at_end=8` + 现有 `complete_percent=90`；低于下限不建续播、超上限标已看并清续播点；`config.DEFAULTS` 同步，缺省行为与现状一致 |
| P0-2 | **JSON 完整备份导出 + 恢复** | 换盘/误删不丢唯一数据库，降低被锁定感 | 中 | 新建 `app/backup.py`；导出 9 张表为单个 JSON（含 schema 版本、导出时间、行数校验）；恢复提供「覆盖 / 仅新增」两种开关；恢复前自动备份当前库；用临时库测试，绝不碰真实 `D:\magicvideo` |

| P0-4 | **文件指纹主键（数据地基第一步）** | 文件移动/重命名后进度不丢，直击播放器通病 | 中 | `media_files`/`watch_progress` 增 `size`/`mtime`/`partial_hash` 列（`_migrate()` 只 ALTER ADD COLUMN，零数据丢失）；按指纹重关联；**保留路径主键兼容**，指纹只做辅助匹配与迁移，不激进替换 |
| P0-5 | **会话切分与真实时长累计** | 防快进到结尾算看完、连播虚增时长、重复计数 | 中 | 会话按「开始/进度/停止」切分，合并重叠区间；同一集只留一个活跃 session；统计口径明确是否含快进/重看/连播（写进 FEATURES） |

| 编号 | 需求 | 价值 | 复杂度 | 验收要点 |

| P1-2 | **清单导入三段式对齐**（核心机会点） | 兑现「输入清单→自动对齐本地文件与历史」的产品定位 | 大 | 支持 MAL XML / Bangumi Takeout JSON；导入预览给差异报告；冲突按 max/不降级/不覆盖规则合并；匹配成功仍须「文件命中 + 标题校验」双判定，禁止直接用 `match_files()` 结论 |

| P1-5 | **刮削限速 + TTL 负缓存 + 强制重刮** | 防封禁、防错误匹配永久固化 | 中 | 请求间隔可配（Bangumi ≥200ms~5s）；成功长期缓存、失败设 TTL；429 退避暂停而非狂重试；提供「强制重刮」入口；本机网络超时时快速降级不变 |
| P1-6 | **导入未匹配「待确认区」** | 不静默丢行、不覆盖手改数据 | 小 | 预览里未匹配项进入待确认列表，用户显式处理；导入幂等，重复导入不产生重复行 |

### 2.4 P3 · 暂缓 / 不做（本版明确排除）

- **暂缓**：换 mpv/libVLC 内核（成本高，当前唯一痛点是倍速精度，已由 P2-5 折中解决；见 OPTIMIZATION §8 结论）、内容哈希识别（大库首次扫描 I/O 重）。
- **不做**：跨设备同步、外部站点双向同步（需服务端/账号/云，与「纯本地、无账号无云」定位冲突，涉及 OAuth 与隐私）。

## 3. 三项补强方向的具体方案

### 方案 A · 数据地基（对应 P0-2、P0-4、P1-3、P1-6）

**问题本质**：三个独立缺陷叠加——① 进度以 `file_id`/路径为键，文件一动就断；② 只有单库无出口，误删全损；③ 主窗口+守护+扫描+备份多进程写，WAL 只解决读写并发不解决写写冲突。

**分步实施**：
1. **先备份，后动主键**（顺序不可颠倒）：P0-2 的 JSON 备份必须先落地并测试通过，再做 P0-4 的 schema 变更。这样即使迁移出问题也有回退点。
2. **指纹做加法不做替换**：`media_files`/`watch_progress` 只 `ALTER ADD COLUMN` 加 `size`/`mtime_ns`/`partial_hash`，保留原路径主键；扫描时填充指纹；重定位/匹配时优先按指纹找，找不到再退回路径。避免一次性替换主键带来的大规模数据迁移风险。
3. **写操作统一收口**：所有写入走 `db.session()` 短事务；全局设 `busy_timeout`；备份导出走只读连接快照，不与守护轮询抢写锁。
4. **回归验证**：P0-4 改动后必须重跑迁移测试（旧库升级、零数据丢失）+ 增量测试；P1-3 补并发写压测。

**风险与对策**：指纹列在旧库上为空 → 首次扫描惰性填充，不阻塞启动；`partial_hash` 只取头尾各 1MB，避免大文件全读；并发写压测在本地临时库跑，不碰真实数据。

### 方案 B · 边界不完整（对应 P0-1、P0-3、P2-5）

**问题本质**：核心功能「能用了」，但参数写死、纠错要逐条点、倍速精度差一个档位，属于「最后一公里」体验。

**分步实施**：
1. **三阈值**（P0-1）：把 `watcher.py` 里硬编码的 `complete_at = db.get_int("complete_percent", 90)` 扩展为四个可配参数，全部进 `config.DEFAULTS`，设置页加输入项。**默认值保持现状**，避免老用户行为突变。判定逻辑：位置比例 < `min_resume_percent` 或播放时长 < `ignore_seconds_at_start` → 不建续播；> `complete_percent` 或剩余比例 < `ignore_percent_at_end` → 标已看并清续播点。
2. **批量纠错**（P0-3）：复用现有 `mark_watched/mark_unwatched/reset_progress` 单个 API，前端多选后循环调用（不新增后端方法）；保持「只改进度表、不删历史」的既有语义。
3. **倍速精度**（P2-5）：在换内核不可行的前提下，把倍速步进默认从 0.1 改为 0.25，使 1.25/1.5/2.0 都能精确命中；这是 OPTIMIZATION §8 明确记录的短期折中。
4. **全盘快搜可达性**（P2-5）：本机 Everything 以 `-svc` 运行导致 es.exe IPC 不通、HTTP 未启用 → 界面在降级到媒体库时明确告知原因和启用步骤（「设置 → Everything → 启用 HTTP 服务器」），**不改 ini、不重启服务**（项目铁律）。

**风险与对策**：三阈值默认值必须与原行为一致，否则老用户续播点丢失；批量操作加二次确认，避免误点清空；倍速步进改动需回归播放控制条的实测用例。

### 方案 C · 外部依赖脆弱（分散在 P1/P2 + 工程加固）

**问题本质**：封面、网页搜索、Obsidian 路线图解析都依赖外部文档结构或站点 HTML，一处改版就静默失效；WiX 安装器属性易回归；缓存键口径曾踩坑。

**分步实施**：
1. **外部解析隔离**：把 AGE/Seeduck 的 HTML 解析收敛到单一适配层（封面与网页搜索已共用硬约束：只认 `data-original`、Seeduck `<h2>`），加「解析失败」告警与降级提示，不再静默返回空；站点改版时只改一处。
2. **缓存键口径统一**：新增任何缓存必须按数据指纹（库路径 + `write_count()` + 行数等），**禁止用文件 mtime**；在 AGENTS §2 已有铁律，本版增加一条测试守护「新缓存键不含 mtime」。
3. **Obsidian 路线图解析解耦**：`parse_roadmap()` 目前硬编码读 `docs/OPTIMIZATION.md` 且依赖 `### P0`~`### P3` 标题 + 数字开头表格行（新文档已刻意避开该格式）。本版给它加契约测试，锁住解析格式；改文档标题结构时必须同步测试。
4. **安装器真机验证**（P2-6）：现有 `verify_install_flow.py` 已在定义层验证属性与升级继承，补一次干净环境的真装真卸，防 WiX 私有属性回归。

**风险与对策**：外部站点解析加超时与单站降级，避免拖垮界面；契约测试失败时给出明确报错（哪个标题/表格缺失），便于快速修复。

## 4. 实施顺序建议

```
P0-2 JSON 备份  ──先落地，作为所有数据变更的安全网──┐
                                                    ├→ P0-4 指纹列 → P1-1 重定位 → P1-2 清单对齐
P0-1 三阈值 + P0-3 批量标记  ──独立小改动，可并行──┘
P0-5 会话切分 → P2-1 时长统计（统计口径依赖会话模型稳定）
P1-3 并发加固  ──贯穿全程，作为数据层改造的配套──
P2 其余项      ──P0/P1 完成后按剩余额力取舍──
```

**建议起步组合**：P0-2 + P0-1 + P0-3（小~中改动、即时收益），随后立刻铺 P0-4 数据地基。

## 5. 版本与发版约束

- 本文件描述 v0.1.6 规划，**不改变当前版本真源**（`app/__init__.py::__version__` 仍为 0.1.5）。
- 按 `AGENTS.md` 铁律：日常迭代只跑增量 `run_changed_tests.py`；**仅当真正发版**（用户明确要求打 tag / 打包）时才升版本、改 `app.js?v`、写 CHANGELOG、同步文档并打 tag。
- 需求落地后，逐条在 `docs/FEATURES.md` 补验收标准、在 `CHANGELOG.md` 记录，并把本文件对应条目标记为已完成。
